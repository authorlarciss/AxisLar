# План реализации AxisLar

Нормативная модель — `lambda/DOMAIN.md`. Этот файл — про порядок работ,
критерии готовности и риски.

## 0. Статус

- M0–M5 — выпущены в 0.1.0 (модель + контракты + in-memory + CLI).
- **Текущая версия — 0.8.0** (contract 4). Выполнено: выделение ядра в
  отдельный проект (0.2.0), контрактный набор хранилищ (0.3.0), порт
  источника и набор источников (0.4.0), семантика синхронизации — Origin,
  tombstone, move по хэшу (0.5.0), tombstone-семантика в порте (0.6.0),
  контрактные наборы источников и политика id (0.6.1), провенанс фасетов
  и слияние по владельцам (0.7.0), переиспользование производных фактов по
  `content_hash` (0.8.0).
- Продукт (AgoraLar) и плагины — отдельные проекты; CLI/HTTP/бэкенды живут
  там.
- Далее: продукт (своё имя, реестр плагинов, простые бэкенды) и плагины
  (отдельные проекты, зависят только от контрактов ядра).

## 1. Что строим и зачем

Ядро многомерного хранилища: оси/фасеты/объекты + запросы, независимое от
бэкенда. Ценность не в коде хранения, а в **зафиксированной семантике**:
пока не решено, что значит `none_of` на разреженном мультизначном
объекте, любой бэкенд будет «прав по-своему». Поэтому первый срез — модель
и in-memory реализация, а не SQL.

## 2. Не цели (v0)

- Второй бэкенд, SQL, Markdown, VaultBridge-адаптер.
- Реестр плагинов, entry points, версия контракта плагинов.
- UI за пределами CLI; мобильные/веб-клиенты.
- Анализ (кластеризация) как код ядра — только швы (`Artifact`, `derived_by`).
- Миграции схемы, удаление/переименование осей, транзакции, индексы.

## 5. ADR roadmap

Нумерация — своя в каждом проекте: здесь она продолжает BaseLar
(0001–0008 наследуются как общие архитектурные решения шаблона), дальше
AxisLar ведёт свою. Старые ADR не редактируются; принятые решения — в
`lambda/adr/`, таблица ниже сверяется с файлами, а не с памятью.

| ADR | Тема | Этап / статус |
|-----|------|---------------|
| 0009 | Многомерная модель: оси, фасеты, объекты | принято |
| 0010 | Разреженность, динамические оси, семантика отсутствующих значений | принято |
| 0011 | Reference-фасеты вместо relations | принято |
| 0012 | Модель запросов: дерево, конъюнкция в v0, `none_of` вместо `!=` | принято |
| 0013 | In-memory backend как референс + контрактные тесты бэкендов | принято |
| 0014 | Снятие pipeline-обвязки шаблона | принято |
| 0015 | Модуль — не слой | принято |
| 0016 | Семантика синхронизации источника | принято (0.5.0) |
| 0017 | Content-addressed кэш производных фактов | принято (0.8.0) |
| 0018 | Владение фасетами и политика слияния | принято (0.7.0) |
| 0019 | Артефакты: байты по хэшу, ссылки из объекта | принято (0.9.0) |
| 0020 | Клиенты, фичи и варианты: `resolve_feature` без состояния | принято (0.10.0) |

Номер следующего ADR — 0021: выдаётся при принятии решения, не заранее.

## 6. Стратегия тестов

- **`tau/alpha`** — инварианты DTO и сериализация.
- **`tau/beta`, `tau/psi`** — фабрики резолверов, сборка, контракты.
- **`tau/delta`** — внутренняя механика `MemoryStorage`.
- **`tau/contract`** — единственное место, где живёт семантика: таблица
  §5, мультизначность, ссылки, разреженность. Параметризуется по бэкенду;
  второй бэкенд подключается одной строкой в фикстуре.
- **`tau/gamma`** — CLI: аргументы и формат вывода, без доменной логики.

Правило: новый бэкенд не считается готовым, пока не проходит
`tau/contract` целиком.

## 7. Риски

| Риск | Признак | Что делаем |
|------|---------|------------|
| Семантика `none_of`/разреженности «поплывёт» в бэкенде | разные ответы у Memory и SQL | таблица §5 как единственный источник истины, контрактные тесты обязательны |
| Модель окажется слишком гибкой и «размажется» | оси с противоречивыми типами, мультизначность-по-умолчанию | `multi`/`strict` явные, инварианты A1–A4 |
| Преждевременная плагинная система | реестр раньше второго бэкенда | швы в v0, реестр в M9 |
| `Entity`/`FacetValue` протекут в `Any` | mypy strict падает | discriminated union, никаких `dict[str, Any]` на границе |
| Смешение с клиентами (UI-логика в ядре) | CLI-ветвления внутри `delta` | `gamma` — тонкий клиент, ядро не знает о представлении |

## 8. Открытые решения (по умолчанию приняты)

| Вопрос | Решение по умолчанию | Пересмотр |
|--------|----------------------|-----------|
| `Entity` vs `Object` | `Entity` | нет |
| `!=` vs `none_of` | только `none_of` | ADR-0012 |
| `id` | UUIDv5 от (`source`, `key`) | ADR-0009 |
| Висячие ссылки | ошибка на запись (`DanglingReference`) | ADR-0011 |
| Категориальная ось | `strict=False` по умолчанию (авто-расширение словаря) | ADR-0009 |
| Порядок выдачи | по `id`, `limit`/`offset` в `QueryResult` | ADR-0012 |
| Плагины | только швы | ADR-0015 |
