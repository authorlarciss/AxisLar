# ADR-0012: Модель запросов — дерево, конъюнкция в v0, `none_of` вместо `!=`

## Контекст

Запрос нужен простой, но расширяемый: v0 — «найди объекты, у которых
`theme contains cyberpunk` и `year_opened >= 2020`». Дальше почти
неизбежно понадобятся `any` (OR), отрицания, `exists` и составные
условия. Если начать с плоского списка фильтров, расширение ломает
публичный DTO.

Отдельный вопрос — `!=`. На мультизначной оси он неоднозначен: «нет ни
одного значения `cyberpunk`» и «есть хотя бы одно значение не
`cyberpunk`» — разные запросы, и оба имеют право называться «не равно».

## Решение

1. **AST — дерево, а не список.** Узел `Query` — `{"all": [Filter, ...]}`;
   `any` и `not` зарезервированы в схеме с самого начала. В v0 исполняется
   только `all`; встретив `any`/`not`, движок возвращает
   `UnsupportedQuery` — то есть отказ явный, а не тихое игнорирование.
2. **Оператор `!=` не вводится.** Вместо него:
   - `contains` — среди значений есть указанное;
   - `any_of` — есть хотя бы одно из перечисленных;
   - `none_of` — нет ни одного из перечисленных;
   - `exists` / `not_exists` — наличие/отсутствие значения по оси.
   Для одиночных осей `none_of` эквивалентен «не равно» без двусмысленности.
3. **Валидация отделена от исполнения.** `IQueryResolver` проверяет запрос
   против `StorageSchema` и `capabilities()` бэкенда (например,
   `QUERY_MEASURABLE`), возвращая исполнимый план или типизированную
   ошибку (`UnknownAxis`, `TypeMismatch`, `UnsupportedQuery`).
4. **Результат — идентификаторы.** `QueryResult(ids, total, limit, offset)`,
   порядок по `id` при отсутствии явной сортировки; полные объекты — через
   `fetch_many(ids)`. Одна форма на все бэкенды.

## Альтернативы

- **Плоский список фильтров (AND по умолчанию).** Проще в v0, но при
  первом же OR меняется форма DTO. Отклонено.
- **`!=` с семантикой «нет такого значения».** Совпадает с `none_of`, но
  читается как «есть значение, и оно другое». Двойное прочтение —
  источник багов. Отклонено.
- **Мини-язык запросов (SQL-подобный / DSL).** Гибко, но требует парсера,
  версии грамматики и документации; для v0 — избыточно. Отклонено;
  AST-дерево даёт 90% пользы без парсера.
- **Возвращать объекты сразу.** Удобно для мелких выдач, но заставляет
  бэкенд тянуть все поля; для больших выдач это дорого. Отклонено.

## Последствия

Плюсы: расширение до `any`/`not` не ломает контракт; мультизначность
описывается однозначно; валидация централизована в резолвере, бэкенд
исполняет уже проверенный план; `capabilities()` не даёт тихо
деградировать.

Минусы: `UnsupportedQuery` для `any` в v0 выглядит как «недоделка» —
это сознательно; клиенту нужно два вызова (`query` + `fetch_many`);
сортировка в v0 фиксирована.

## Статус

Принято.
