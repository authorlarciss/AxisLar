# ADR-0013: In-memory backend как референс + контрактные тесты бэкендов

## Контекст

Реализаций планируется несколько: память, JSON, SQLite, позже адаптеры
внешних источников. У каждой — свои ограничения (SQL не умеет «нет
значения» без отдельной таблицы; JSON не умеет индексы; внешний источник
может не поддерживать ссылочную проверку).

Если первым писать SQL, семантика модели будет выведена из удобства SQL:
появятся `NULL`, дефолты, `!=` через `NOT IN`, и «правильный» ответ
станет определять бэкенд, а не модель.

## Решение

1. **Первая реализация — `MemoryStorage`**: словари и списки, никакого
   SQL. Её задача — доказать, что модель и семантика непротиворечивы, и
   служить эталоном для остальных.
2. **Семантика проверяется контрактным набором** (`tau/contract/`),
   параметризованным по фабрике бэкенда:
   - таблица отсутствующих значений (`DOMAIN §5`) — каждый ряд таблицы
     отдельный кейс;
   - мультизначность: `contains` / `any_of` / `none_of`;
   - разреженность и динамические оси (старые объекты после `add_axis`);
   - reference-фасеты: `contains`, `DanglingReference` на запись;
   - кардинальность (`multi`), лимиты/смещения, детерминированный порядок.
3. **Второй бэкенд не считается готовым, пока не проходит контракт
   целиком.** Подключение — одна строка в фикстуре параметризации.
4. **`capabilities()` — часть контракта.** Бэкенд объявляет, что реально
   умеет (`QUERY_MEASURABLE`, `QUERY_REFERENCE_CHECK`, `WRITE_BULK`, ...);
   `IQueryResolver` обязан отвергнуть запрос, который бэкенд не
   поддерживает, вместо тихой полной проверки в обход индексов.

## Альтернативы

- **Начать с SQLite.** Раньше даёт «настоящее» хранилище, но семантика
  модели подстраивается под SQL, а не наоборот. Отклонено.
- **Тестировать каждый бэкенд своими тестами.** Тесты дублируются и
  расходятся; расхождение обнаруживается пользователем. Отклонено.
- **Один набор тестов «на все случаи» без параметризации.** Невозможно
  подключать частичные реализации (например, read-only бэкенд). Отклонено.

## Последствия

Плюсы: эталонная семантика зафиксирована кодом и тестами; второй бэкенд
подключается дешево и проверяется строго; `capabilities()` делает
ограничения явными.

Минусы: контрактный набор придётся расширять вместе с моделью (это
работа, а не бесплатно); `MemoryStorage` не даёт представления о
производительности — индексы и планировщик появятся вместе со вторым
бэкендом.

## Статус

Принято.
