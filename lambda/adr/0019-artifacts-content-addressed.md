# ADR-0019: Артефакты — байты по хэшу, ссылки из объекта, контракт 5

## Контекст

До 0.8.0 модель умела хранить «факты о объекте»: скаляры, фасеты,
провенанс. Артефакты (превью, эмбеддинги, транскрипты) оставались
обещанием: ADR-0017 зафиксировал, что они адресуются содержимым и
дедуплицируются, но ни DTO, ни порта не было. Из-за этого reuse по
`content_hash` переносил только фасеты, а «тяжёлые» данные пришлось бы
класть в продукт — то есть в место, которое не знает модели.

Границы, которые нельзя размыть:

- артефакт — не фасет: фасет отвечает «какое значение по оси», артефакт —
  «где лежат байты»;
- артефакт не принадлежит объекту: две копии одного файла должны
  ссылаться на одни байты;
- бэкенд, который артефактов не умеет, обязан **отказать**, а не отдать
  пустоту.

## Решение

1. **`Artifact(content_hash, media_type, data)`** — DTO уровня `alpha`.
   Инвариант DTO: `content_hash` = sha256(`data`), проверяется на
   создании. `size` — свойство, а не поле: размер, который можно
   рассинхронизировать с данными, хранить незачем.
2. **`ArtifactRef(content_hash, media_type, size, derived_by)`** — ссылка
   из объекта под ролью (`preview`, `embedding`, ...). Роль — ключ
   `Entity.artifacts`, поэтому у объекта может быть несколько артефактов
   разного назначения, а имена ролей не обязаны совпадать с осями.
3. **Дедупликация — свойство модели, а не оптимизация.** Ключ артефакта —
   хэш. Повторная запись тех же байтов идемпотентна и не создаёт второй
   копии. Тот же адрес с другим `media_type` — `ArtifactMismatch`: два
   описания одних байтов движок не разгадывает.
4. **Порт расширен четырьмя методами:** `put_artifact`, `get_artifact`,
   `list_artifacts` (только метаданные), `delete_artifact`. Это ломающее
   изменение поверхности — **контракт 5**.
5. **Возможность `Capability.ARTIFACTS`.** Бэкенд без неё возвращает
   `UnsupportedArtifact` на запись и удаление, `None` на чтение,
   пустой список на перечисление. Проверка ссылок выполняется только при
   объявленной возможности — как с `REFERENCE_CHECK`.
6. **Cсылка на отсутствующий артефакт — `DanglingArtifact`,** но только
   когда бэкенд умеет артефакты и получил `known_artifacts` (иначе
   проверка невозможна, и это не ошибка объекта).
7. **Удаление только явное и только без ссылок.** `ArtifactInUse`, если на
   артефакт ссылается любой сохранённый объект, включая tombstone:
   воскрешение объекта не должно оставлять его без данных. Автоматического
   GC нет — в v0 удаление делает вызывающий, осознанно.
8. **Источники артефактов не порождают.** `IEntitySource` по-прежнему
   отдаёт объекты; наполнение артефактами — работа анализатора (клиент,
   плагин, скрипт), который сначала кладёт байты, потом ссылку. Это
   оставляет синхронизацию простой: она не тянет блобы.

## Альтернативы

- **Артефакты в продукте** (sidecar-таблица `hash → blob`). Ядро не
  меняется, но дедупликация, ссылки и инвалидация живут в оболочке; у
  второго клиента (бот, HTTP-клиент) появляется второй источник истины.
  Отклонено: решение меняет логику модели, значит его место — в ядре.
- **Байты внутри `Entity`** (`dict[str, bytes]`). Объект раздувается,
  каждая копия объекта тащит блоб, дедупликация невозможна. Отклонено.
- **Потоковый API** (`open_artifact() -> AsyncIterator[bytes]`) сразу.
  Нужен для больших файлов, но вводит владение ресурсом и отмену в порт,
  который пока прост. Отложено до появления реального потребителя.
- **Автоматический GC по недостижимости.** Требует обхода всех объектов и
  политики гонок; в v0 это явная команда. Отложено.

## Последствия

Плюсы: тяжёлые данные не покидают модель; дедупликация и ссылочная
целостность проверяемы контрактным набором; бэкенд без артефактов
корректен, если честно отказывает.

Минусы: контракт 5 — все плагины и продукт обновляются синхронно;
артефакты грузятся в память целиком (`Artifact.data: bytes`); ссылки не
участвуют в запросах (нельзя «найти объекты с превью» — для этого нужен
фасет-маркер). Всё это осознанно на текущем этапе.

## Реализация (0.9.0)

- `alpha`: `Artifact`, `ArtifactRef`, `content_hash_of`, `make_artifact`.
- `beta`: `validate_artifact`, `validate_entity(known_artifacts=...)`.
- `delta`: четыре метода в `IStorageEngine`, реализация в `MemoryStorage`,
  `Capability.ARTIFACTS`.
- `iota`: `run_storage_contract` проверяет артефакты (дедупликация,
  метаданные, конфликт media_type, ссылка, занятость, удаление) и
  корректный отказ бэкенда без возможности.
- `Core`: методы-делегаты, чтобы продукт не ходил в хранилище напрямую.

## Статус

Принято, реализовано в 0.9.0 (контракт 5).
