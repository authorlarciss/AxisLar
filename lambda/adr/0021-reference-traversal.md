# ADR-0021: Обратные ссылки — отдельный порт и индекс

## Контекст

Ссылка в модели — не сущность, а фасет на оси с типом `reference`
(DOMAIN §1). Запросы умеют фильтровать по такой оси (`eq`, `any_of`,
`none_of`), но не умеют отвечать на вопрос «кто указывает на этот
объект». А без него невозможны ни граф связей, ни проверка «что сломается,
если удалить объект», ни навигация «где ещё упоминается».

Два ограничения задавали выбор:

- **Обход — не запрос.** `Query` — это фильтр по фасетам самого объекта.
  Входящие ссылки лежат в чужих объектах, то есть требуют обратного
  индекса, а не ещё одного оператора.
- **Не все бэкенды обязаны это уметь.** Порт `IStorageEngine` — контракт
  хранения; если добавить в него абстрактный метод, сломаются все
  существующие плагины, а контракт придётся поднимать до 6.

## Решение

1. **Новый DTO `ReferenceLink(axis, entity_id)`** в `alpha`: входящее
   ребро — это ось, по которой сослались, и объект-источник. Ось
   обязательна: две ссылки на один объект по разным осям — разные рёбра,
   и продукт (граф, карточка) должен их различать.
2. **Отдельный порт `IReferenceIndex`** в `delta`, рядом с
   `IEntitySource`. Причина та же, что и там: это другая роль, а не другая
   реализация хранения. `IStorageEngine` не тронут.
3. **Возможность `Capability.TRAVERSE_REFERENCES`** — бэкенд объявляет,
   что порт реализован. Потребитель проверяет `isinstance(storage,
   IReferenceIndex)`; отсутствие возможности — не ошибка, а состояние
   («этот бэкенд не умеет обход»).
4. **`references_to(entity_id, axes=None, *, include_deleted=False)`**:
   `axes=None` — все оси; пустая последовательность — ни одной (пустой
   результат, а не «все»); ссылки из tombstone по умолчанию скрыты,
   `include_deleted=True` возвращает и их. Порядок детерминирован: по оси,
   затем по `id` источника.
5. **Индекс строится по всем ссылкам, включая tombstone.** Видимость
   решается на чтении: иначе воскрешение объекта требовало бы
   переиндексации, а «кто на меня ссылался, пока я был удалён» терялось бы
   безвозвратно.
6. **Индекс поддерживается на записи, а не пересчитывается на чтении.**
   `MemoryStorage` хранит `цель → ось → источники` и обновляет вклад
   объекта в `upsert`/`bulk_upsert` (снять старый вклад, добавить новый).
   Пересчёт «с нуля» стоил бы O(n) на каждый запрос графа.
7. **Контракт остаётся 5.** Изменение аддитивное: новый DTO, новый порт,
   новая возможность. Существующие плагины работают без изменений;
   не реализовавшие порт просто не объявляют возможность. Версия ядра
   поднимется на релизе, как в ADR-0020.

## Альтернативы

- **Метод в `IStorageEngine`.** Проще для потребителя (нет проверки
  `isinstance`), но ломает всех реализаторов и требует контракта 6 ради
  возможности, которая нужна не всем. Отклонено.
- **Оператор в `Query`.** Не выражает обратное направление: запрос
  фильтрует объект по его фасетам, а не находит объекты по чужим.
  Отклонено.
- **Отдельная сущность «ребро».** Превращает модель в граф и ломает
  DOMAIN §1 («отношений как отдельной сущности нет»). Отклонено: обход —
  проекция, а не второй вид данных.
- **Пересчёт индекса при каждом чтении.** Проще в реализации, непригодно
  для графа: раскрытие узла стало бы O(n). Отклонено.

## Последствия

Плюсы: появляется язык для обратных ссылок; бэкенды подключаются
опционально; удаление и «что сломается» можно проверить до записи;
граф и навигация получают опору в ядре, а не в UI.

Минусы: индекс удваивает часть состояния в памяти (для in-memory бэкенда
это цена, для внешних — обязанность поддерживать его в транзакции с
записью); `IReferenceIndex` не входит в контрактный набор
`run_storage_contract` — плагин может объявить возможность и реализовать
её неверно. Следующий шаг — контрактный набор для порта (как
`test_storage_contract` для хранения).

## Статус

Принято, реализовано в `nu` (контракт 5, версия ядра — на релизе).
