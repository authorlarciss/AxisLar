# ADR-0024: Ревизии объектов и оптимистичная блокировка

## Контекст

До сих пор `upsert` означал «заменить по `id`»: две вкладки, CLI и UI,
редактор и фоновый импорт молча перетирали друг друга — выигрывал последний
записавший. Пока продукт был read-only, это не проявлялось. Появление
редактора (фаза 3 продукта) делает это блокером: человек правит фасет в
браузере, в это же время синхронизация пишет объект из источника, и правка
исчезает без следа.

Нужен механизм, который: (а) обнаруживает конфликт, (б) не требует
транзакций и блокировок от бэкенда, (в) переносится на HTTP как `ETag`.

## Решение

1. **`Entity.rev: int`** — номер версии объекта. Ставит **бэкенд** при
   записи: `1` при создании, `stored + 1` при обновлении. Присланное
   клиентом значение игнорируется: ревизия — свойство хранилища, а не
   пожелание клиента.
2. **`upsert(entity, *, expected_rev: int | None = None)`**:
   `None` — без проверки (импорт, синхронизация); `0` — «создать, объекта
   быть не должно»; `N > 0` — «изменяю ревизию N». Несовпадение — ошибка
   `CONFLICT`, и в хранилище не пишется ничего.
3. **`bulk_upsert` ревизии не проверяет**, но ставит их: это путь импорта и
   `sync`, где конфликт не имеет смысла (источник — владелец фактов). Для
   пакетной правки из UI есть `bulk_patch` на уровне продукта: он читает
   объекты, применяет операции и пишет через `upsert` с ожидаемыми
   ревизиями.
4. **HTTP отдаёт `ETag`** из ревизии и содержимого; `If-Match` со значением
   из `ETag` превращается в `expected_rev`. Так редактор получает
   конфликт вместо потери данных.
5. **Контракт 6.** Изменение ломающее для реализаций порта (новая
   сигнатура `upsert`), поэтому версия контракта поднимается; плагины
   объявляют `requires_contract >=6,<7`.
6. **Откат — не часть ревизий.** `rev` отвечает на «кто последний», но не
   хранит историю. Undo требует журнала изменений: он живёт в продукте
   (`beta`), потому что это операция над последовательностью действий, а не
   свойство объекта. Ядро остаётся без истории: его задача — не дать
   потерять данные молча.

## Альтернативы

- **Метка времени `updated_at` вместо счётчика.** Не даёт «ожидаемой
  версии»: время может совпасть, а часовые пояса и точность часов — новый
  источник ошибок. Отклонено.
- **Блокировки на время правки.** Требуют состояния на сервере и
  «протухания»; для локального однопользовательского продукта это лишняя
  механика. Отклонено.
- **История в ядре (event sourcing).** Дорого и навязывает всем бэкендам
  формат журнала. Отклонено: журнал — продуктовый слой.
- **`expected_rev` в `bulk_upsert`.** Импорт не должен падать из-за
  параллельной правки: источник — владелец своих фасетов (ADR-0016).
  Отклонено.

## Последствия

Плюсы: конфликт обнаруживается до записи; редактор получает `ETag`/`409`;
контракт не требует от бэкендов транзакций; ревизия едет в документе, то
есть работает и в файловом сторе.

Минусы: контракт 6 (плагины обновляют диапазон); `rev` есть в каждом
документе — при сравнении «до/после» его надо исключать; бэкенд обязан сам
считать ревизию, а значит `upsert` в SQL-сторе делает дополнительное чтение
текущего документа.

## Статус

Принято, реализовано в ядре 0.13.0 (контракт 6).
